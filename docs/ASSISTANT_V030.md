# 做饭小助手（v0.3.0 开发中）

首页“开始烹饪”进入原有选餐页，小助手与按钮共用同一套业务。无模型、AI API、学习任务或联网依赖。聊天条件仅保存在当前页面，不自动保存为长期偏好。

## 首批说法

- “两个人吃”“两人份”“我们俩”“我俩”“改成三个人”“换成三个人”：沿用 1–12 人限制，重新推荐并重算份量。
- “清淡点”“吃清淡一点”：筛选清淡标签，使用标签稳定 code，不依赖显示名称。
- “不要辣”“别放辣”“不吃辣”：选择清淡标签，并保守排除菜名、食材及备注、步骤中的常见辣味词；这不保证描述不全的菜谱一定不辣，界面明确要求核对。
- “简单点”“简单吃点”“做点简单的”“别太麻烦”“还是太麻烦”“快手菜”：筛选快手菜；再次简化后最多两道，保留当前人数和口味。
- “推荐一下”“换一套”：生成方案或依次查看本批方案；没有更多方案时明确告知。
- “换掉汤”“这个汤不要了”“汤换一个”“再换一个汤”：先点选一套方案；恰好一道汤时保留其他菜，重新计算整餐并核对。无汤、多汤、没有替代汤时解释并提供原有选餐/手动入口。汤由稳定标签 code 识别。
- “看看缺什么”“看备料”“开始做饭”：打开核对页，不直接执行写入；用户仍需点击“确认，开始烹饪”。
- “重新开始”：清除本轮条件和待确认方案，回到默认两人。

人数和口味/繁简短语可交换顺序、连续组合，不要求逗号或固定口令，例如“两个人简单吃点”“今晚我们俩，简单吃点，别放辣”。未知片段、不同人数、相反条件和冲突动作拒绝整句话，保持原条件；平时隐藏整排示例按钮，澄清时才显示少量选项。不会通过“最后一个关键词获胜”猜测含义。

“换一个”在有方案时换整套；刚成功换汤后“再换一个”继续换汤。本轮连续换汤会累计排除先前换掉的汤；没新汤时保留原餐，其他整套候选仍可切换。改条件、重新生成或重选方案会清除汤指代与换汤排除；刷新页面也不保留这些会话状态。

“可以，就这个”“就吃这套”只进入备料核对，仍需原确认按钮。支持明确取消“取消清淡”“辣不辣都行”“不用简单”；“不要太辣”“微辣”会说明不能区分辣度，询问是否改成不辣，不自动等同不辣。“不要简单的”仍拒绝，不会误设为简餐。

“半小时搞定”会按已识别人数和口味生成候选并提示没有可靠整餐耗时，可再选快手近似方案；不会承诺完成时间。条件与“看备料/换汤”同句变化时先重算、要求重选方案，不沿用旧确认。生成失败显示失败原因，不显示成功文案。

## 业务保护

只扩展原有 `POST /api/recommendation/meal-plans` 的可选 `assistant` 筛选：`light`、`no_spicy`、`simple`、`keep_recipe_ids`、`exclude_recipe_ids`、`replacement_role`。入参通过既有严格 schema 校验，保留 ID 去重、存在性及条件一致性检查。换汤将固定菜纳入候选窗口，并枚举剩余位置；不在旧缺料表上拼接。

推荐输出每道菜新增 `is_soup`，支持标签改名。无助手参数时原有推荐路径保持相同人数、排序、去重及库存规则。

所有需求、缺料和快照复用既有服务。条件变动后旧方案失效；在途旧响应被序号丢弃；换汤在途时禁止确认与评价写入。最终确认仍走原有 `apply`、快照和持久幂等流程。进入烹饪不预扣库存；结算继续沿用既有页面和服务。

安卓通过既有离线路由和共享页面取得相同功能；Windows 复用网页。未新增迁移或修改保质期、数据库恢复及签名逻辑。

## 本餐临时聊天（0.3.0-preview.4）

选餐页的小助手改为可收起气泡聊天面板。最多40条消息仅存在当前RecommendPage内存；收起不清空；重新开始清空消息、待澄清问题、当前方案和本餐条件；离开选餐（包括进入烹饪）或关闭应用后清空，下次选餐新开。不向数据库、localStorage、sessionStorage写聊天记录。不是长期记忆或学习功能，也未引入模型/AI API。

未知片段会提供先前已识别的只读条件，不立即应用；用户明确选择“仅按已懂条件找菜”后才按这些条件推荐，未知忌口仍需用户核对。普通追加条件保留尚未处理的要求；明确“我的意思是…”可重新表述。冲突人数/否定不进入部分确认。“换一个”先问范围，短答“汤”/“整套”接上；刚成功换汤后的“再换一个”仍按汤解释。取消追问不改本餐，重新开始重置。待澄清时原确认按钮禁用，handleApply也有同步兜底，不允许待确认要求被旧方案确认绕过。

## 单步换汤撤回与变化提示（0.3.0-preview.6）

支持“撤回换汤”“撤回上一次换汤”“刚才那个汤还是要吧”“换回原来的汤”。只保留最近一次成功换汤前的菜谱ID和排除集，不保存可重新提交的旧快照。撤回调用只读推荐接口 exact_keep=true 固定原菜清单，重新读取库存和菜谱、计算整餐备料/缺料及新snapshot；支持原餐1–4道菜，不自动补菜。空清单、缺失/不符合条件菜、重复ID、与换汤/排除参数混用会拒绝。

换汤和撤回保持其余菜的位置；在核对区域显示旧汤→新汤，在汤菜项显示文字标记和底色。撤回成功后单步记录清空，失败保留当前方案和重试机会。改人数（包含手动人数输入）、口味、筛选、重新生成、重选或评价时撤回失效；新一餐/离开页面自然清空。写入和扣库存路径不变，旧确认和幂等意图在成功换汤/撤回后作废。

41项聊天纯函数+98项隔离API检查通过。Windows包内Electron 38.8.6/原生SQLite完成8项临时库验证，包含exact_keep原菜清单重算。浏览器独立临时库实测：甲→乙（其他菜保持原位）→模拟503撤回失败仍保留乙→库存新增7克→重试撤回甲，需求表读取2007克新库存→再次换汤→手动改成3人→撤回失效。没有创建烹饪会话或扣库存（仅显式测试增加7克）。

本轮旧DSH临时配对记录不存在，未成功联络或取得独立审查，不把尝试发送当已联系。独立验证由Lumi完成。安卓共享生产构建/类型检查通过，原生运行时未改，不重复启动模拟器全套测试。

## 入口、明确状态与指定食材/菜系（0.3.0-preview.7）

会话列表“新建烹饪会话”与首页“开始烹饪”统一进入人数→选餐/助手→核对流程，此时不调用createSession。独立“手动选菜”按钮保留原创建空白会话路径，历史会话详情逻辑不变。安卓App覆盖文件已同步同一导航回调，保留其返回键历史处理；核对覆盖差异后更新共享App哈希基线。

助手采用“已有要求/已识别（待确认）/未处理/处理状态/生成结果/下一步”等字段，不用拟人寒暄。纯生成成功会报告实际方案数；未知片段按逗号分片收集，识别到后续食材或菜系也不自动应用。已知食材名主要从真实食材定义加载，菜系名从真实cuisine分类标签加载；另识别用户明确要求的牛肉、川菜、西餐词汇，其含义不代表数据库有菜谱或有库存。这里只支持正向指定食材和一个菜系；不把“不要牛肉”当成要牛肉，不实现食材排除/过敏保障。不限食材/不限菜系可清除相应要求。

推荐只读参数ingredients（最多4个定义名称）要求每个食材至少出现在整餐一道菜中，不强迫每道配菜都含牛肉；cuisine要求全部候选菜谱有相应cuisine标签。食材参与组合校验，并固定部分食材候选防止40道候选截断遗漏。无匹配返回0，不自动放宽；库存仅影响真实匹配/缺料信息，指定想吃不表示家里已有。所有后续换汤和撤回也沿用这些条件。
