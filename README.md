# HomeChef

家庭食材库存管理工具。

HomeChef 的核心目标是管理家中已有的食材及其库存：记录家里有什么、有哪些可用的叫法、有多少、什么时候入库的、什么时候过期，并在使用食材后手动扣减相应库存。

当前版本 **v0.2.3**，包含食材库存、菜谱（五分类 Tag + 单菜喜欢/不喜欢）、烹饪结算与本地规则整餐推荐（历史衰减 + 确定性轮换）。当前不接入 AI。

---

## 当前已实现功能

**菜谱标签与偏好（v0.2.3）**

- **五分类 Tag 管理**：菜品类型 / 口味 / 烹饪方式 / 用餐场景 / 菜品特点；32 个系统预设 + 自定义 Tag，
  均可新建、改名、改分类、删除（删除前显示关联菜谱数，只清关联、不删菜谱）；分类字典来自后端，不在前端写死。
- **Tag 筛选**：`AND`（全部满足）/ `OR`（任一满足）两种模式，选择与模式持久化。
- **单菜喜欢 / 不喜欢 / 取消**：只作**软权重**（喜欢 +40 / 不喜欢 −80），**不会把菜谱排除出推荐**。
- **内容包（可选导入，不是默认附带）**：`server/seed/v023-content/` 提供 30 道家常菜与食材定义，
  幂等、只新增、可重复运行（CLI 默认 dry-run）。
  ⚠️ **不导入时不会"自带 337 个定义 / 36 道菜谱"**；仓库**提供内容包文件**，但**不会自动导入数据库**；本机**测试库存不随仓库分发**。

**推荐精度与结算一致性（v0.2.3 修复）**

- 推荐优先**库存充足**、优先消耗**临期**；未知用量明确提示；过期库存不计入可用；不做单位换算。
- 推荐与结算共用同一套「按份数**逐行缩放并舍入再合并**」的需求口径，
  消除「推荐可做、结算却库存不足」以及**配料行顺序影响结论**的问题。
- 临期收益按结算 **FEFO 实际分配**计算，不再虚报"会用掉临期食材"。
- 结算预览改为**库存副本 + 真实需求顺序**分配：跨菜共享不重复显示可扣；
  `ready`（无待确认项）与库存是否充足（`stock_sufficient`）分开显示；预览**不写库**。
- 调味品按 **presence（只记有无）** 语义统一：需要用户**明确确认**「不按量扣减」，确认后才记 `skipped_user`。
- 显式零需求量按零需求处理，不再提示"未指定用量"。
- 结构搭配只做**粗略类型搭配**提示（主食/荤/素/汤等），**不是精确营养计算**。
- **需要迁移 `0012_v023_tags_preference`**（新增 `recipe_preference`；`recipe_tag` 增 `category` / `code` / `is_system` / `sort_order`）。
  新安装按现有迁移流程执行；已升级到 `0012` 的库无需再迁移。

**整餐推荐与烹饪（v0.2.2）**

- 从中式灶台主页开始，按人数查看最多 5 套整餐方案，展开每道菜的配料和步骤。
- 合并整餐食材需求，展示库存满足情况、缺料数量和临期优先理由；推荐不扣库存。
- 菜谱暂按两人份为基准换算；不做单位换算，未知用量需核对，推荐排除过期库存。
- 确认后进入既有烹饪流程并在结算时扣减；保留手动选菜、烹饪记录改名和多选删除。
- 方案确认前数据变化会要求重新生成；短期重复请求去重不跨服务重启。

详细规则、限制和隔离验证见 [v0.2.2 开发交接](HANDOFF_V022.md) 与 [独立验收](SOL_ACCEPTANCE_V022.md)。

**食材库（Ingredient Definition）**

- 食材定义：默认名称 + 别名 + 允许单位 + 预计保质期 + **分类**
- 每个食材定义拥有稳定的内部 ID（SQLite `AUTOINCREMENT`，删除后不复用）
- 重命名不改变 ID，改分类也不改变 ID；所有业务关联都通过 ID，而不是名称
- 食材库搜索（默认名称与别名的包含匹配，可返回多个结果）
- 别名管理：新增、修改、删除、**设为默认名称**
- 允许单位管理：新增、移除（**调味品允许 0 个单位**）
- **统一保存**（v0.1.4）：名称、分类、保质期、别名、单位、设为默认
  全部先改草稿，点「保存」时**在同一个事务内一次性提交**；
  取消或关闭会丢弃全部未保存修改
- **名称排序**：A → Z / Z → A
- **分类筛选**：可按分类过滤，并与搜索、排序组合使用
- 删除食材定义（存在任何库存记录时被拒绝）

**库存（Inventory）**

- 一个食材定义可以有 **0 到多条**库存记录（例如「土豆 3 个」「土豆 1 袋」「土豆 1 千克」）
- 多条记录**不会自动合并**，也不做跨单位汇总
- 每条库存记录可**独立**查看、编辑、删除、消耗
- 消耗后自动扣减；消耗数量不能超过当前库存（不允许负库存）
- 消耗到 0 后数据库记录**保留**，但当前库存列表隐藏 `quantity = 0` 的记录
- **排序**：默认（临期优先）/ 保质期 / 入库日期 / 名称 / 数量，均支持正反序
- **分类颜色标签**（v0.1.4）：每个食材名称右侧显示所属分类标签，
  颜色取自该分类配置的颜色，文字颜色按背景亮度自动选用深色或白色
- **分类筛选**

**日期与临期**

- 入库日期（代码字段 `purchase_date`，必填，默认当天）
- 生产日期（`production_date`，可为空）
- 到期日期（`expiry_date`，可为空）及其来源（`expiry_date_source`：`estimated` / `manual`）
- 未填写到期日期时，按食材定义的预计保质期自动估算
- 用户手动填写的到期日期**永远优先**，且不会被自动覆盖
- **临期状态**：无保质期 / 正常 / 临期 / 已过期，在库存列表中可视化标记
- 已过期状态**优先于**临期；到期当天算临期

**设置**

- 临期预警规则可配置：**天数阈值** 或 **百分比阈值**
- 百分比按 `ceil(总保质期天数 × 阈值 / 100)` 折算成天数后比较
- 分类管理入口
- **分类颜色**（v0.1.4）：在分类管理内为每个分类单独配置颜色，
  内嵌颜色选择器（色相条 + 取色区 + HEX 输入）+ 12 个常用预设

**食材分类**

- **19 个默认分类**：蔬菜、水果、水产、蛋类、豆制品、乳制品、主食/谷物、
  干货/菌菇、冷冻食品、调味品、其他/饮品、猪肉、牛肉、羊肉、其他畜肉、
  鸡肉、鸭肉、鹅肉、其他禽肉
- 支持用户**自定义分类**（新建 / 删除）
- 仍被食材使用的分类**拒绝删除**
- 食材库与库存均可按分类筛选

> `冷冻食品` 指食材**本身就是**冷冻 / 速冻成品或半成品（如冷冻饺子、汤圆、薯条）。
> 普通牛肉即使保存方式是冷冻，分类**仍然是牛肉**。

**调味品**

- 调味品是 **presence-only**：只记录「有 / 无」，**不管理数量**
- 无需填写允许单位，也无需保质期
- 库存列表显示为「有」，不显示数量 / 单位 / 日期 / 储存方式
- 不参与临期计算
- 普通食材与调味品之间**不允许直接切换库存分类**（语义不同，需删除后重新添加）

**其他库存属性**

- 储存方式（常温 / 冷藏 / 冷冻）
- 备注

**数据校验**

- 数量必须是有限的非负数字
- 单位必须属于固定枚举，且必须在该食材定义允许的单位内
- 日期关系校验（生产日期不晚于入库日期；手动到期日期不早于入库日期）
- 分类名称唯一（自动 trim，空名称与重名被拒绝）

**菜谱管理**（v0.2.0）

- **菜谱列表**：三行布局 —— 第一行「新建菜谱」入口；第二行名称搜索（左）+ 排序（右）；
  第三行已选 Tag（左）+「选择 Tag」按钮（右）
- **名称搜索**：只匹配菜谱名称，大小写不敏感、子字符串匹配
  （⚠️ **Tag 名称不参与搜索**；想按 Tag 找菜谱请用 Tag 筛选）
- **Tag 筛选**：独立弹窗，支持多选与 **AND / OR** 两种模式，可在弹窗内新建 Tag；
  已选 Tag 可在工具栏逐个移除
- **排序**：最近修改时间 / 创建时间 / 菜谱名称 × 升序降序
- **设置持久化**：排序字段、排序方向、Tag 选择与 AND/OR 模式写入数据库，刷新后保留；
  **搜索词不持久化**
- **新建菜谱**：名称、描述、多项配料（食材 + 数量 + 单位 + 备注，**允许重复选择同一食材**）、
  Tag 多选；保存失败保留输入可重试
- **菜谱详情**：展示名称、描述、Tag 与食材明细（名称 / 数量 / 单位 / 备注 / 顺序），
  无描述 / 无食材 / 无 Tag 时给出明确提示
- **菜谱编辑**：从详情进入，完整回填原有数据，可增删改食材行与 Tag；取消不产生写入
- **菜谱删除**：详情页入口 + 二次确认；取消确认不会调用删除 API
- **库存搜索**：库存页新增搜索栏，按**库存记录对应的食材名称**本地过滤，
  与分类筛选、排序并行工作

## 技术栈

| 层 | 技术 |
| --- | --- |
| 前端 | React + TypeScript + Vite |
| 后端 | Node.js + TypeScript + Fastify |
| 数据库 | SQLite + Drizzle ORM |

不使用 Redux / Zustand 等全局状态管理，前端使用原生 `fetch` 与 `useState`。

## 本地运行

需要 Node.js 20 或更高版本。

安装依赖（在仓库根目录执行）：

```bash
npm install
```

### 数据库 migration

HomeChef 使用 Drizzle 迁移管理数据库结构。首次运行需执行：

```bash
npm run db:migrate --workspace server
```

- migration 文件位于 `server/drizzle/`
- 数据库文件生成在 `server/data/homechef.db`（已被 `.gitignore` 忽略）

其他数据库脚本：

```bash
# 生成新的 migration（修改 schema 后）
npm run db:generate --workspace server

# 可视化查看数据库
npm run db:studio --workspace server
```

### 启动后端

在仓库根目录执行：

```bash
npm run dev:server
```

- 地址：http://localhost:3001
- 健康检查：http://localhost:3001/health

> 端口可用 `PORT` 环境变量覆盖。

### 启动前端

另开一个终端，在仓库根目录执行：

```bash
npm run dev:client
```

- 地址：http://localhost:5173

Vite 开发服务器已配置代理，会把 `/api` 请求转发到后端 `http://localhost:3001`，因此本地开发无需额外配置跨域。

### 构建

```bash
npm run build
```

## 首次运行

除了 migration 之外，还需要导入内置食材数据（229 个食材定义）：

```bash
npm run db:seed --workspace server
```

seed 是 **INSERT-only** 的，不会覆盖用户自己的修改，可以安全地重复执行。

## 测试与验证情况

当前项目**尚未配置自动化测试框架**（没有 Vitest / Jest 等），
前端也没有测试框架，仅通过 `tsc` 与 production build 验证。

后端验证使用 TypeScript 脚本（`server/verify-*.ts`），通过 `tsx` 运行，
覆盖真实 HTTP 请求 + 真实 SQLite：

```bash
cd server
npx tsx verify-v013.ts
```

这些脚本：

- 使用**独立临时数据库**与**动态端口**（避免污染开发库、避免端口冲突）
- 输出 `[PASS]` / `[FAIL]` 计数，失败时以非零状态码退出
- 覆盖数据库结构、Service 行为、API 端到端行为、错误码与数据完整性

断言总数会随版本变化，请以各脚本的实际输出为准，本文档不再记录固定数字。
